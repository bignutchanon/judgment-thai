# Web research: glyph width / character spacing problem in RGG Dragon Engine fonts

Date: 2026-08-20. Scope: web-only research (no local file access, no game files touched). Question: has anyone, for any Dragon Engine (or older RGG engine) game, in any language, solved the problem where codepoints >= 0x80 render at fixed full-cell pitch and ignore per-glyph advance, while codepoints < 0x80 get proportional/half-width treatment? Our team already verified this locally on Yakuza 6 (2,990 advance values edited in the font file, zero visible effect on screen for glyphs placed in non-ASCII/donor slots).

Bottom line up front: **nobody has publicly documented a fix.** No writeup, tool, ASI plugin, or fan translation was found that (a) reverse-engineers a width-class table in the Dragon Engine font format, or (b) hooks the text renderer to force proportional spacing for donor-slot glyphs, or (c) demonstrates narrow spacing by relocating non-Latin glyphs into the ASCII 0x20-0x7E range. This is a genuine gap in public knowledge, not a search failure — see the "search coverage" section at the end for what was tried.

## 1. Other-script mods on RGG/Yakuza games, and what they did about spacing

### Thai
- **CLAIMED** — Judgment `MOD2SUB TH EN google V1` (nexusmods.com/judgment/mods/228), Kiwami `mods/431` and `459`, Kiwami 2 `mods/702`, Like a Dragon Gaiden `mods/239`, Yakuza: Like a Dragon `mods/197`, Lost Judgment `mods/472` — all by the same "MOD2SUB"/Thai-fan-MT lineage (uploader `Maimaomaiplae` and others). Descriptions only say "แปลเกมบางส่วนเป็นภาษาไทย โดยใช้ AI" (partial AI translation) and give install steps (copy files, RyuModManager). **None of the mod pages document font/glyph/spacing work.** The Gaiden page does list `font.aston.par` among the files it overwrites (fetched via r.jina.ai proxy, since nexusmods 403s direct WebFetch), which is **VERIFIED only as "a font.par gets replaced,"** not as evidence of any width fix — no readme, changelog, or screenshot caption discussing spacing was found on any of these pages, and Nexus comment/image tabs returned no text content through automated fetch (likely JS-rendered; not capturable via WebFetch/r.jina.ai as configured). Given these are explicitly Google-MT quality mods (per our own CLAUDE.md guidance to treat them only as proof-of-concept, never as TM), and given no spacing discussion surfaces anywhere in their public materials, the working assumption should be that they either accepted the same wide/ugly spacing our team observed, or restricted Thai text to contexts (subtitle-style overlays implied by the "2SUB" naming) where it was tolerable. This could not be confirmed either way — treat as an open question, not a lead.
- A standalone "Yakuza 0 Thai Mod Localization" (nexusmods.com/yakuza0/mods/1112) exists but Yakuza 0 predates Dragon Engine (different font/engine generation entirely), so it's not informative for Judgment.
- One Reddit-adjacent/forum data point (found via search snippet, not independently opened): a modder attempting Yakuza 0 → Thai reported Thai glyphs simply **would not display in-game** and they were stuck converting TTF → DDS by hand with no success — i.e., a documented failure, not a solved case. **CLAIMED**, single search-snippet source, could not verify further.

### Vietnamese
- **CLAIMED** — "MeVietHoa" group has released a Google-Translate-based Vietnamese patch for Yakuza: Like a Dragon (voz.vn/t/yakuza-like-a-dragon-viet-hoa-gg-dich.1069810) and mentions "mình đã xử lý được font và text" ("I got the font and text working") — **no technical elaboration** was present on the fetched page; it's a download-link post, not a devlog.
- **CLAIMED** — viethoagame.com has an active recruitment thread specifically for a Ryu Ga Gotoku translation team covering Like a Dragon, Judgment, and Lost Judgment (viethoagame.com/threads/lap-team-dich-cho-nhung-du-an-viet-hoa-game-cua-studio-ryu-ga-gotoku…). The thread confirms font/text handling has been done ("mình đã xử lý được font và text" appears here too) but again **no width/spacing technical detail** is on the page as fetched.
- Net result: Vietnamese teams claim to have working fonts for Dragon Engine RGG titles, including Judgment/Lost Judgment specifically, but **no public technical writeup of how the width/spacing problem was handled** could be found. Vietnamese needs narrow proportional Latin-based glyphs plus stacking diacritics — the same category of problem as Thai — so if they solved it, it wasn't written up anywhere indexable. Worth a direct approach (Discord, forum DM) if the team wants a real answer here; that's outside this research's reach.

### Arabic
- **CLAIMED** — An independent, still-in-progress Yakuza 0 Arabic translation (YouTube "Yakuza 0 Arabic Translation Showcase" by a solo student translator, and a separate "تعريب ياكوزا زيرو" video) exists, plus references to a Discord server and to using **ParManager** (Kaplas80's PAR archive tool — verified below to be archive-only, no font/glyph logic) to pack/unpack files. Yakuza 0 is pre-Dragon-Engine, so not directly transferable, and no RTL or width-handling detail surfaces in the available snippets. Steam discussion threads referenced in search results (steamcommunity.com/app/638970/discussions/0/3118158126042046198 and /1739964766316096193) could not be read — Steam's mature-content interstitial blocks both WebFetch and the r.jina.ai proxy from reaching the actual thread content.
- No Dragon Engine (Y6+) Arabic project was found at all.

### Hebrew / Devanagari / Greek / Cyrillic (as a target script, not donor)
- No mods found for Hebrew or Devanagari on any Yakuza/Judgment title.
- Cyrillic: Russian localization writeups exist (see below) but for **pre-Dragon-Engine** titles (Yakuza 0, Kiwami, 5 Remastered) and describe reusing spare Western-European accented-Latin slots (À, Æ, Ö, etc. — i.e. still within a single-byte extended-Latin/CP1252-style table, not a >=0x80 "donor slot" scheme comparable to ours), not a >=0x80 fixed-pitch problem. Not directly transferable.

### Chinese / Korean (native support, not a mod)
- Judgment/Lost Judgment ship official EN/JA plus the **Retrial** fan-made expanded-language-support mods (`nexusmods.com/judgment/mods/203`, `nexusmods.com/lostjudgment/mods/641`) which add/restore Traditional Chinese, Simplified Chinese, and Korean text-language options via Shin Ryu Mod Manager. These are primarily gameplay/balance mods (porting Lost Judgment combat tech back to Judgment) that happen to also carry language-pack switching; their pages do not document any Latin/UI spacing change. Since CJK is naturally full-width, it structurally can't reveal anything about narrow-glyph handling — as expected, no lead here confirms or denies whether Latin spacing was ever touched by these language packs.

## 2. Public reverse-engineering of the Dragon Engine text renderer / width classification

**Negative result.** Extensive search (English, Chinese, Russian) found no public document, GitHub repo, GBAtemp/romhacking.net thread, or wiki page that describes:
- a half-width/full-width (or "width class") flag or byte in the Dragon Engine `FONT!`-format font file,
- a codepoint-range classification table (e.g. "cp < 0x80 → half pitch") in the renderer,
- or a pitch/advance calculation routine for the in-game text layout engine.

What exists instead, all **VERIFIED by direct fetch**:
- **RyuModManager / Shin Ryu Mod Manager** (github.com/SutandoTsukai181/RyuModManager, github.com/SRMM-Studio/ShinRyuModManager) — file-redirection ASI loaders only. They hook file *loading* paths so loose files in a `mods/` folder override PAR contents. No text-rendering or glyph-metric hooking of any kind.
- **DragonTweak** (originally github.com/Lyall/DragonTweak, migrated to codeberg.org/Lyall/DragonTweak — README fetched directly) — an ASI plugin with a documented, exhaustive feature table across every RGG PC title (Kiwami 3, Pirate Yakuza, Infinite Wealth, Gaiden, Lost Judgment, Judgment, Kiwami 2, Yakuza 6, Yakuza 0, Kiwami, Yakuza 3/4/5 Remastered). Its only features are: disable pillarboxing/letterboxing, adjust shadow quality, adjust LOD, skip intro logos. **No text/font/UI feature exists in this plugin at all.**
- **BEPEdit** (github.com/HeartlessSeph/BEPEdit) — despite initially looking font-adjacent, this edits the "BEP" format (a different Dragon Engine binary asset type, unrelated to fonts/text) and is explicitly marked outdated in favor of `Fronkln/HActLib`'s "AuthEdit"; nothing about glyphs.
- **ParManager** (github.com/Kaplas80/ParManager, repo contents listed directly via `gh api`) — handles only the PAR archive container format (extract/repack, SLLZ decompression including the V2 variant used by Kiwami 2). Its `ParLibrary/Converter` folder contains only PAR archive reader/writer classes — **no font, DDS, or glyph converter exists in this repo.** It is a container tool, not a font tool.
- **TranslationFramework2** (github.com/Kaplas80/TranslationFramework2) — issue #20 "Font for Yakuza 0" could not be read (GitHub blocked both WebFetch and the r.jina.ai proxy with 403 on this specific URL), but search-result snippets describe an executable-side "char spacing" table with a manual/auto-adjust feature and a separate `hd2_hankaku.dds` texture. This is for **Yakuza 0's older (pre-Dragon) engine**, and notably that engine already appears to keep a *separate* half-width ("hankaku") font texture/sheet from the main one — i.e., the older engine sidesteps the ASCII/non-ASCII pitch problem by using an entirely different glyph sheet for half-width text, rather than one shared table with mixed pitch rules. Whether Dragon Engine (Y6+) still has any equivalent "hankaku sheet" concept is unknown from public sources; **our own font.judge/Y6 data uses a single `tbgm_0p_ja` sheet for everything**, so if a hankaku/zenkaku split ever existed in this lineage, it isn't visible in the shipped Dragon Engine font asset our team already surveyed.

Chinese-language search ("如龙 字体 修改 汉化", "如龙7/8 字体 宽度") surfaced only Chinese fan-patch download pages (3DM, 游侠网, 游民星空) for pre-Dragon titles (Yakuza 0, Kiwami) where the "font fix" is simply swapping a bundled TTF file (`3dm.ttf`) — implying those older engines route through a system/TTF font path for at least some UI text, a different architecture than Dragon Engine's baked bitmap-atlas `FONT!` format. One Baidu Tieba thread that looked promising (`tieba.baidu.com/p/9072300090`, "向各位大佬求教关于嵌字的问题" — asking for help with text typesetting/insertion) returned HTTP 403 + CAPTCHA wall on both WebFetch and the r.jina.ai proxy and could not be read.

Russian-language search found detailed russification writeups on DTF.ru for Yakuza 5 Remastered and Yakuza 0/Kiwami (pre-Dragon engine). The most detailed one fetched directly (dtf.ru/games/4722895, Yakuza 5 Remastered) describes a "Kamuro-Design" 4K font atlas approach that **repurposes unused Western-European accented-Latin character slots** (À, Æ, Ö, etc.) to carry Cyrillic glyphs, explicitly to get clean high-res rendering — but the article contains **no discussion of VWF/advance-width tables, half-width/full-width classification, or spacing metrics**, despite search-snippet teasers (before direct fetch) suggesting VWF-table content existed. A separate DTF article on the original Yakuza 5 russification mentions searching for a "VWF table" to prevent Cyrillic from running together, confirming **older, non-Dragon RGG engines do have an editable VWF offset table** the Russian community has located — but this predates Dragon Engine and no equivalent was found for Y6+.

## 3. Chinese/Korean fan text and whether Latin/UI spacing was ever touched

No evidence either way. CJK fan patches and the official zh/ko language options in Judgment/Lost Judgment (via Retrial) were the only leads, and none of their public pages (mod description, install instructions) mention adjusting Latin character spacing or editing a font width table. Because CJK glyphs are inherently full-width and thus never exercise the half-width code path, a CJK-only patch has no structural reason to touch it, and apparently none did as far as public documentation shows.

## 4. ASI/DLL plugins hooking text rendering (beyond Parless/SRMM-style file loading)

**Negative result**, fairly conclusively. DragonTweak's README was fetched directly and is the most actively maintained general-purpose Dragon Engine tweak plugin covering essentially the whole modern RGG PC catalog (as of the version checked) — its feature list (letterboxing, shadows, LOD, logo skip) contains nothing about text, fonts, or rendering hooks. RyuModManager/ShinRyuModManager are confirmed file-redirection loaders, not renderer hooks. No other ASI plugin targeting text/font rendering in any RGG PC title surfaced in English, Chinese, or Russian search terms ("Yakuza ASI plugin text", "Dragon Engine hook font", "如龙 ASI 字体", etc. — the Chinese/Russian phrasing of this specific sub-question returned no relevant hits beyond what's already covered above).

## 5. Evidence about ASCII-slot (0x20-0x7E) placement yielding narrow proportional spacing

**No direct evidence found, positive or negative.** No mod was found that documents replacing Latin letters (a-z, A-Z, or punctuation) with glyphs of another script within the ASCII range specifically in order to inherit the half-width/proportional code path. This is exactly the kind of thing that, if it worked, would likely be undocumented anyway (modders often just do it and ship without a technical writeup) or it may simply never have been tried this way — none of the Thai/Vietnamese/Arabic mod pages found describe *where* in the font's codepoint space their new glyphs live, only that "font and text" were made to work. Given our team's own verified finding (donor slots >= 0x80 ignore per-glyph advance and use fixed full-cell pitch, confirmed by a null-effect edit of 2,990 advance records), and given the total absence of any public counter-evidence, **the ASCII-slot hypothesis remains untested by anyone publicly documented** — it is worth our team trying directly rather than expecting to find a public precedent.

Sites that block scraping (Nexus Mods pages beyond basic description text, Steam Community discussion threads behind the mature-content gate, some GitHub issue pages, Baidu Tieba) were retried through `https://r.jina.ai/<url>` per instructions; several still returned 403 or stripped-down content (noted inline above) and their content could not be recovered by any means available in this session. Nexus Mods "Posts" and "Images" tabs in particular appear to be JS-rendered and returned no usable text through either WebFetch or the jina proxy — a human with a browser could likely extract more from those tabs (screenshots showing actual in-game spacing quality, and any comments about readability) than this research could reach.

## Practical implication for this project

Given the negative result across the board, the JETH team should treat the glyph-width problem as **unsolved in public knowledge** and plan to solve it independently rather than search further for a ready-made fix. The two most promising untested directions surfaced by this research, neither verified by any external source, are:
1. Test whether placing Thai glyphs in the ASCII 0x20-0x7E codepoint range (item 5 above) yields proportional spacing, since that's the only codepoint range our own Y6 findings already confirm honors per-glyph advance.
2. If a hankaku-style separate half-width glyph sheet concept exists anywhere in the Dragon Engine renderer (as it apparently does in the pre-Dragon Yakuza 0 engine per the `hd2_hankaku.dds` naming), that would be a second avenue — but nothing public confirms or denies this for Y6+/Judgment, so it would require local investigation of the game's renderer/shaders rather than more web search.
