## 4. ฟอนต์ — สถาปัตยกรรมที่พิสูจน์บนจอแล้ว (รอบ 1-12, 15-20 ส.ค. 2026)

> ⚠ **ล้าสมัยบางส่วน** — ข้อสรุปเรื่อง advance ("ตาราง width อยู่ใน exe" · "ไม่มี cp ไหน
> advance 0" · "ต้อง pre-compose") ถูกล้มแล้วใน **§4c** ส่วนโครงไฟล์/atlas ยังถูกต้อง


**ข้อสรุปเดียวที่สำคัญที่สุดของโปรเจกต์นี้: โหมด EN ของเกมวาดข้อความ *ทุกชั้น* ด้วย
`meta_ot_cond_book.dds` ตัวเดียว** — หน้าไตเติล · จอโลโก้ (Press any button) · UI เซฟ/โหลด ·
**ซับบทสนทนา** (ยืนยันรอบ 12 ด้วยการแทนบทพูดทั้ง 19,055 บรรทัดใน `talk.bin` ด้วยข้อความทดสอบ
ที่ encode สองแบบพร้อมกัน: donor ของฟอนต์ไตเติลขึ้นอ่านออก · donor ของ `tbgm_0p_ja` ขึ้นเป็น tofu)

ผังตารางที่ decode จากไฟล์จริง:

| สมบัติ | ค่า |
|---|---|
| atlas | 512 x 1536 px · BC4U · ไม่มี mip |
| ตาราง | 16 คอลัมน์ x 24 แถว = **384 เซลล์** · cell 32 x 64 px |
| การแม็ป | เซลล์ `n` = cp เมื่อ cp < 0x80 · เซลล์ `n` = cp − 0x20 เมื่อ cp ≥ 0xA0 (**ข้าม C1 block**) |
| ครอบคลุม | U+0000–007F แล้วต่อด้วย U+00A0–019F (Latin-1 + Latin Extended-A) |
| หมึกเดิม | Latin-1 61 เซลล์ · Ext-A 8 เซลล์ (`Ā ā Ō ō Œ œ Ū ū`) ที่เหลือว่าง |
| metrics | ink เริ่ม x≈2 · baseline y≈44 · cap height ≈25 px |
| ตาราง width | **อยู่ใน `Judgment.exe` ไม่ใช่ในไฟล์ data** (ไม่มี `.bin` คู่กับ dds เลย) |

ข้อเท็จจริงที่ได้จากการทดสอบบนจอ (แต่ละข้อ = หนึ่งรอบ deploy + ผู้ใช้แคปภาพ):

1. **เขียนกลิฟไทยทับเซลล์แล้วขึ้นจอจริง** ทั้งเซลล์ที่มีหมึกเดิมและเซลล์ว่าง (รอบ 3)
   → ไม่มีปม "เซลล์ว่าง = tofu ถาวร" แบบ Y6
2. **advance ผูกกับ codepoint ของ donor ผ่านตาราง width ใน exe ไม่ใช่รูปที่เราวาด** (รอบ 4)
   `ก` ตัวเดียวกันบน donor แคบ (`¡ ¹ Í Ì Ï`) เรียงชิดกว่าบน donor กว้าง (`Ò Ó Ô Õ Ö`) ชัดเจน
   → **เลือก donor = เลือกความกว้าง ทำได้หมดในชั้น data ไม่ต้องแตะ exe/DLL**
3. **ไม่มี codepoint ไหน advance = 0** (รอบ 5-6 · ทดสอบ 10 ตัว: NBSP, soft hyphen, `¨`, `´`,
   `¡`, U+0001, U+0005, U+000E, U+001F, U+007F — แยกหนึ่งตัวต่อหนึ่งแถว)
   ทุกตัววาดออกมาจริงแต่กินที่แนวนอนหมด · กลุ่ม control ได้ระยะเท่ากันทุกตัว = ค่า default ของตาราง
   → **มาร์กลอยแบบ per-char เป็นไปไม่ได้ ต้อง pre-compose ฐาน+มาร์กเป็นกลิฟเดียว**
4. **ขยาย atlas ไม่ได้** (รอบ 7) ขยายภาพเป็น 2240 px + แก้ `dwHeight`/`dwPitchOrLinearSize`
   ให้ตรงสูตร BC4 แล้ว แต่ในเกมเมนูอังกฤษเละทั้งจอ (`"licen e nfo ma ion"`) = engine ยึดขนาด
   ตารางเดิมไว้ ไม่อ่านความสูงจาก header → **เพดาน 384 เซลล์เป็นเพดานถาวร**
5. **ขนาดตัวอักษรต้องมาจาก ppem เดียว** (รอบ 8-9) renderer สเกลกลิฟทีละตัวให้ ink สูงเท่ากัน
   ตัวที่มีหางบน (`ใ ไ โ ป ฝ ฟ`) จึงถูกย่อจนเล็กกว่าเพื่อน — แก้โดยใช้ ppem เดียว (ตั้งจาก `ก`
   = 22px) แล้ววางตามเส้นฐานจริง · มาร์กวางเป็นชั้นเหนือ ink ของฐานที่วัดจริง · บีบแนวนอนไม่เกิน 15%
   **ห้ามกลับไป normalize ความสูงรายตัวเด็ดขาด**
6. `tbgm_0p_ja` (7,093 กลิฟ · slot ว่าง 2,157) **ไม่ถูกใช้เลยในโหมด EN** — งาน donor Cyrillic +
   record cp ไทยที่เพิ่มไว้ในไฟล์นั้นเก็บไว้เผื่อโหมด JA เท่านั้น
7. cp ที่ไม่มีในตาราง = วาดเป็น **กล่อง tofu** (ไม่ใช่ว่างเปล่า) — ใช้เป็นสัญญาณ debug ได้

## 4c. ⭐ ตาราง advance อยู่ใน `font.bin` — ไม่ใช่ exe (22 ส.ค. 2026 รอบ 16)

**ข้อสรุปนี้ล้ม §4 และ §4b บางส่วน** — อ่านหัวข้อนี้เป็นตัวจริง

### ที่อยู่

```
data/db.judge.en.par
  └── en/font.bin                      ARMP v2 · 25 แถว (หนึ่งแถวต่อฟอนต์หนึ่งตัวในเกม)
        ├── คอลัมน์ bin_exists / adjust_scale / draw_scale / draw_scale_hankaku
        └── คอลัมน์ kerning_table       ARMP ซ้อนอีกชั้น · 332 แถว x 6 คอลัมน์ (type 7 = float)
              แถวที่ 17 = "meta_ot_cond_book"  (แถว 18 = ตัวเอียง)
```

หมายเลขแถวของ `kerning_table` = **เลขเซลล์ใน atlas** (cp < 0x80 → cp, cp >= 0xA0 → cp - 0x20)

### สูตร

```
advance  = 36 - 18.0 x (L + R)
x_offset = -18.0 x L
```

โดย (L, R) = คอลัมน์ (1,2) หรือ (3,4) หรือ (5,6) ตาม "ขนาดวาด" ที่ชั้น UI นั้นเรียกใช้
หน่วยเป็นครึ่ง em (เซลล์เต็ม = 2.0) → `L + R = 2.0` ได้ advance = 0 · เกินกว่านั้นติดลบได้

**การยืนยัน (สองทางอิสระ):**

| วิธี | ผล |
|---|---|
| fit กับ probe หวีของเราเอง 171 จุด (คู่คอลัมน์ 5,6 · K = 18.00) | คลาดเคลื่อนเฉลี่ย **0.27 px** · สูงสุด 2.0 |
| fit กับภาพในเกมของ MOD2SUB (คู่ 3,4) | **rms 0.23 px** |
| ตรวจกับฟอนต์อังกฤษเดิม | `36 - 18.0 x R` ≈ ขอบขวา ink + 3.5 px ทุกตัว (M a b c x m w …) |

### หลักฐานว่าใช้ได้จริง (ม็อด MOD2SUB)

* แก้ `font.bin` **71 แถว** ช่วง cell 0x81-0x14B = ช่วง donor เดียวกับเรา
* `ui.judge.en/en/font/common_font.bin` ของเขา **เหมือนต้นฉบับ 100%** (ยืนยันว่าไม่ใช่ตาราง metrics)
* ไม่แตะ exe · atlas ของเขา **ไม่มี pre-compose เลย** — ถอดสตริงจาก par ของเขาแล้ว
  `เอาชนะพวกอันธพาล` = 16 codepoint ต่อ 16 ตัวอักษร แต่ในภาพสระ/วรรณยุกต์ซ้อนบนฐานถูกต้อง
* ตัวอย่างค่าของเขา: `ั` = U+00B4 → (L, R) = (1.20, 0.95) → advance = -3.8 px · เลื่อนซ้าย 22.2 px
* `reARMP` decode→encode `font.bin` ได้ 26,048 → **26,064 ไบต์ เท่ากับของเขาเป๊ะ** = ใช้เครื่องมือเดียวกัน

### ผลที่ตามมา

1. **มาร์กตั้ง advance = 0 ได้** → เลิก pre-compose ฐาน+มาร์ก · หนึ่งตัวอักษรหนึ่งเซลล์
2. **ฐานตั้ง advance = ความกว้าง ink + side bearing** → เพดาน 36 px ของเซลล์ว่าง Ext-A หายไป
3. **Latin Ext-B (U+0180-019F) ขึ้นเป็นกล่องเปล่าเพราะตารางมีแค่ 332 แถว** = ถึง cell 331 = U+016B
   ไม่ใช่เพราะ atlas และไม่ใช่ "เอนจิ้นไม่มี mapping" → donor pool ที่ใช้ได้จริงจบที่ **U+016B**
4. `translations/donor_widths.json` (advance เดิมที่วัดด้วย probe หวี) **ไม่ได้ใช้จัดสรรอีกแล้ว**
   เก็บไว้เพราะมันคือชุดข้อมูลที่ใช้ยืนยันสูตรข้างบน

### สิ่งที่ตรวจแล้วว่า **ไม่ใช่** ตาราง (อย่าเสียเวลาซ้ำ)

`meta_ot_cond_book.dds` ไม่มี `.bin` คู่ · `gothic.bin`/`symbol.bin` correlation < 0.3 ·
`ui.judge.en.par → en/font/*.bin` 36 ไฟล์เป็นตาราง cp → sprite index ของฟอนต์ตัวเลข UI ·
สแกน `Judgment.exe` (394 MB) และ RAM (5.6 GB) ด้วยลายเซ็น advance ทั้งสองแบบ — ไม่เจอ

## 5. ระบบ slot allocator — `scripts/slot_alloc.py`

> ⚠ หัวข้อนี้อธิบายระบบ **ก่อนรอบ 16** (จับคู่ donor ตามความกว้าง + pre-compose คลัสเตอร์)
> ระบบปัจจุบันคือหนึ่งตัวอักษรหนึ่งเซลล์ + variant ของมาร์ก — ดู `docs/slot_alloc.md`
> (สร้างอัตโนมัติ) และ docstring ของ `scripts/slot_alloc.py`


โจทย์: มีเซลล์จำกัดตายตัวและต้องแบ่งกันทั้งเกม (ไตเติล + UI + ซับ ใช้ตารางเดียวกัน)
ทางแก้: allocator กลางตัวเดียวที่ตัดสินว่าเซลล์ไหนได้ช่อง แล้วเขียนผลเป็น **`translations/slotmap.json`**
ซึ่งทั้งฝั่งฟอนต์ (วาดกลิฟลง atlas) และฝั่งข้อความ (encode เป็นสตริง donor) อ่านร่วมกัน — map เดียว
ห้ามมีสำเนาที่สอง (กติกาเดียวกับ `master_th.json`)

### แหล่ง donor (แบ่งชั้นตามความเสี่ยง)

| ชั้น | ช่วง | ช่อง | สถานะ |
|---|---|---|---|
| `latin1_letter` | U+00C0–00FF | 64 | พิสูจน์แล้วทุกจอ (รอบ 3/8/9/11/12) |
| `exta` | U+0100–019F | 160 | เซลล์ว่างเติมได้จริง (รอบ 3 กลุ่ม B) · advance ปกติ (รอบ 4) |
| `latin1_symbol` | U+00A0–00BF | 32 | ใช้ได้ แต่ชนสัญลักษณ์ที่ EN ใช้ (`¥ © ® ±`) → ถูกหักออกอัตโนมัติ |
| `control` | U+0001–001F (เว้น tab/LF/CR) + U+007F | 29 | ⛔ ปิดไว้ — วาดได้จริง (รอบ 6) แต่ยัด control char ลง db เสี่ยงกับ parser |
| ASCII U+0020–007E | — | 95 | **ห้ามแตะ** เกมใช้พิมพ์อังกฤษ (LICENSE/CREDITS คงอังกฤษ) |

### การกันชน (สองทาง — ทั้งคู่คิดอัตโนมัติจากข้อมูลจริง)

- **ฝั่งอังกฤษ**: สแกน `extracted/unique_strings.json` (ผลของ §2) หา cp ในช่วง pool ที่ข้อความ
  อังกฤษของเกมใช้อยู่ → 18 ตัว (`NBSP ¥ © ® ± à á ã ä ç é ê í ñ ó ö ú ü`) ถ้าเอาไปทำ donor
  ข้อความอังกฤษที่คงไว้จะกลายเป็นไทยมั่ว
- **ฝั่งไทย**: สแกนคลังแปลไทย หา cp ในช่วง pool ที่ *คำแปล* ใช้ → เพิ่มอีก 4 ตัว (`° · × ÷`)
  (เจอจริงจากคลัง K3: `36.5°C`, `${num1}P×${num2}`)
- รวมสงวน **22 ช่อง** → pool ใช้ได้จริง **234 ช่อง**
- `SlotMap.encode()` ยังกันซ้ำอีกชั้น: ถ้าข้อความมีตัวอักษรที่ถูกใช้เป็น donor อยู่ มันจะหยุด
  พร้อมบอกว่าตัวไหน (ให้ไปแก้ในขั้น QC) แทนที่จะปล่อยให้เพี้ยนในเกม

### นโยบายแบ่งเซลล์

**ฐาน + มาร์ก 1 ตัว** ประกอบเป็นกลิฟเดียวต่อเซลล์ · มาร์กตัวที่ 2 ขึ้นไปแยกเป็นเซลล์ของตัวเอง
(มีช่องสำรองให้มาร์กเดี่ยวครบทั้ง 16 ตัว) — ทางเลือก "รวมทุกมาร์กเป็นกลิฟเดียว" กินช่องมากกว่าโดย
ได้ความครอบคลุมน้อยกว่า จึงไม่เลือก

### ลำดับการจัดสรร

1. **บังคับ**: พยัญชนะ 44 + สระ/สัญลักษณ์ที่กินที่แนวนอน 11 (`เ แ โ ใ ไ า ะ ำ ๅ ๆ ฯ`) +
   มาร์กเดี่ยว 16 → พิมพ์คำอะไรก็เรนเดอร์ได้ ไม่มีทางเจอ tofu
2. **cluster ตามความถี่จริง** จากคลังแปลไทยที่ ship แล้วสามภาค (K3 35,573 + Gaiden 23,633 +
   Y6 37,209 = **96,415 ประโยค / 3,228,722 cell occurrence**) — คลังของโปรเจกต์นี้เอง
   (`translations/master_th.json`) จะถูกนับรวมอัตโนมัติเมื่อมี และถ่วงน้ำหนัก x3
3. **จับคู่ donor ตามความกว้าง**: donor ที่รู้ความกว้างจริง (วัด ink จาก atlas ต้นฉบับ) มีน้อย
   จึงยกให้เซลล์ที่ความถี่สูงสุดก่อน แล้วจับคู่กันเองตามความกว้าง · ที่เหลือได้ donor เซลล์ว่าง
   ที่ยังไม่รู้ความกว้าง (ทำเครื่องหมาย `width_unknown` ไว้)
